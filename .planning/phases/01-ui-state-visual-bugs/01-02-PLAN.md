  <action>
The blue rectangle artifact persists DESPITE widget recreation after generation. Investigate and fix the actual root cause.

**Architecture context (already discovered):**

The post-generation flow is:
```
audio_service.py:_on_generation_success() (line 334)
  -> audio_mapper.py:update_marker_list() (line 1323)
    -> DESTROY all MarkerRow widgets (lines 1326-1328)
    -> CREATE new MarkerRow widgets (lines 1331-1333)
      -> marker_row.py:load_waveform() (called in constructor, line 179)
        -> WaveformManager.extract_waveform_from_audio() (line 355)
        -> draw_waveform() or draw_waveform_placeholder() (lines 361/363)
```

The refresh_waveform() method added in plan 01-01 is orphaned -- never called because widgets are destroyed/recreated.

**Diagnosis steps -- check each of these possible root causes:**

1. **Timing issue with update_marker_list()**: `_on_generation_success()` (line 353) calls `update_marker_list()` which recreates all widgets. But on line 356, `hide_marker_progress(marker_index)` is scheduled for 500ms later, referencing the NEW widget that never had progress shown. Check if `show_marker_progress` on the OLD widget (called at line 230 before generation thread) or `hide_marker_progress` on the NEW widget causes visual artifacts.

2. **Double call to update_marker_list()**: `generate_marker_audio()` at line 227 calls `update_marker_list()` to show "generating" status. Then `_on_generation_success()` at line 353 calls it AGAIN. Both calls happen on the main thread but with the generation thread in between. Check if the first call's widgets get left in a stale visual state before being destroyed.

3. **Canvas not fully repainting inside scrollable container**: MarkerRow widgets are packed inside `marker_rows_frame` which is inside `marker_canvas` (a Canvas used for scrolling). When all children of `marker_rows_frame` are destroyed and recreated rapidly, tkinter may not fully repaint the container canvas, leaving ghost artifacts. The fix would be to force a canvas repaint after widget recreation.

4. **MoviePy AudioFileClip caching**: `extract_waveform_from_audio()` opens the audio file with MoviePy's AudioFileClip. Check if MoviePy or ffmpeg caches file data, causing the old waveform to appear for the new file.

5. **load_waveform() silent failure**: If `load_waveform()` fails to find the audio file (path mismatch between what was saved and what's looked up), it shows a placeholder text. But if `extract_waveform_from_audio()` returns valid-looking but stale data, the old waveform gets drawn. Add debug logging to `load_waveform()` to print which file path it resolves and whether extraction succeeds.

**Implementation approach:**

After diagnosing which root cause applies, implement the fix. The most likely root causes and their fixes:

**If timing/canvas repaint issue (most likely):**
- In `update_marker_list()` in audio_mapper.py, add `self.marker_rows_frame.update_idletasks()` AFTER destroying old widgets but BEFORE creating new ones, to force the canvas to process the destruction
- Also add `self.marker_canvas.update_idletasks()` after the scroll region configure to force full repaint

**If load_waveform() loads stale data:**
- Add a small delay before loading waveform in newly created widgets after generation, using `self.frame.after(50, self.load_waveform)` instead of calling `self.load_waveform()` synchronously in the constructor
- OR: Don't call load_waveform() in the constructor at all -- call it after all widgets are created in update_marker_list()

**If the issue is that refresh_waveform() should be used instead of recreation:**
- Modify `_on_generation_success()` in audio_service.py to NOT call `update_marker_list()` (which destroys all widgets). Instead, update only the affected marker's row widget:
  ```python
  # Instead of destroying all widgets, just refresh the specific one
  if 0 <= marker_index < len(self.gui.marker_row_widgets):
      row = self.gui.marker_row_widgets[marker_index]
      row.marker = self.gui.markers[marker_index]  # update reference
      row.refresh_waveform()
      row.update_display()
  ```
  This avoids widget recreation entirely and uses the refresh_waveform() fix from plan 01-01.

**Regardless of root cause, also ensure:**
- Add debug print in `load_waveform()` showing which audio path was resolved (or "not found")
- Add debug print in `draw_waveform()` confirming successful draw with sample count
- These prints help future debugging and can be removed later

**Important constraints:**
- Do NOT change the draw_waveform() rendering logic -- it draws correctly when given correct data
- Do NOT change WaveformManager.extract_waveform_from_audio() -- it extracts correctly
- The fix must be in the WIRING between generation completion and waveform display update
- Test by reading the code flow after your fix to confirm the chain: generation completes -> version data updated -> correct audio file loaded -> waveform drawn
